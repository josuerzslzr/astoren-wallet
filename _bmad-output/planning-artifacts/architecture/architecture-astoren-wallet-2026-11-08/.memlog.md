- (decision) Ledger truth (user): ledger entries are the source of truth; balances are a cached projection updated in the same DB transaction; drift is a reconciliation failure (SM-2). Prevents: balance updated without ledger record or vice versa.

Go-live changes only partners. Prevents: duplicate verifiers/dedupe tables drifting across deposits and withdrawals.
- (decision) Money representation: amounts as bigint integer minor units; JSON {amountMinor: <integer>, currency: 'USD'|'EUR'}. Rates as numeric(18,8) in Postgres, decimal library in TS (never JS number arithmetic), decimal string in JSON. fx-sim emits 5-decimal strings (OANDA-style). One shared convert(amountMinor, rate, rounding) function is the only place conversion rounding happens. Prevents: float drift, divergent rounding sites.
- (decision) Rounding (user: 'to the house'): in every conversion the payer side rounds up and the receiver side rounds down to whole minor units; any difference (0 or 1 minor unit) is credited to a house rounding/fee revenue system account, in P2P takes too. Keeps journals balanced per currency. Sub-cent effect cannot breach SM-1 ceiling.
- (event) Researched FX API rate formats (2026-11-09): OANDA v20 prices are strings, 5 decimals for EUR_USD; Wise /v1/rates rate is a JSON number; Stripe FX Quotes separates base_rate vs exchange_rate (wire type unconfirmed). Market convention: EUR/USD 4 decimals + 5th pipette.
- (decision) Rates per direction (user): market rate, house quote and pegged offers are held per direction (USD->EUR, EUR->USD); the percentage (house spread, peg margin) is applied over each direction's own rate. Open: sign/quote convention so builders apply percentages the same way, and how the per-direction market rate is derived from the FX feed.
- (decision) Price convention (user, supersedes per-direction rate storage): single source of truth. Every stored price is in one unit, USD per 1 EUR: market mid (one stored value from FX feed), offer price + side (gives EUR | gives USD), house price computed per side from mid. Maker peg margin stored as entered against the canonical price. convert() multiplies or divides by the price per side; no inverted rate is ever stored. House spread formula fixed: taker receives (1 - spread) of market value (house cost = exactly spread, matching SM-1). 'Better for taker' and FR-21 worse-than-house checks are side-aware. Rates are displayed per taker direction (e.g. EUR per USD) at display time only. Side/bid/ask terms stay internal; never in UI. Prevents: two builders inverting or applying margins differently.
- (direction) Rate display direction toggle (user idea): UI lets a user show rates as USD per EUR or EUR per USD, for makers and takers. Architecture rule: server always sends the canonical price; client computes the inverse with the decimal library at display time; presentation only, never affects settlement. Amounts from convert() are authoritative; displayed rates are rounded to 4-5 dp; cost % is direction-independent.

- (decision) Race mechanism (user): conditional update ('guarded transition': UPDATE business row ... WHERE state=expected AND conditions RETURNING; 0 rows = refused, nothing else touched). FR-19 'arrival order' = order Postgres grants the row lock. Rejected: in-memory matching engine (stateful SPOF, DB stops being truth), optimistic version retries.
- (decision) Global lock order (user): business row first (offer / withdrawal / deposit request), then ledger accounts by ascending account id. Prevents: deadlocks between use cases written independently.
- (decision) Idempotency (user): client generates Idempotency-Key once per intent (per preview/confirm sheet), reuses it on every retry, new key only on a new intent. Server table idempotency_key unique (user_id, key) with request hash, status, stored response; same key + different body = 422; refusals stored as outcomes too; keys expire ~24h. Concurrent duplicate waits on the unique index inside the same transaction and replays the stored response (user: avoids false 'lost funds' alarms). Rejected: Stripe-style 409 in-progress.
- (decision) Guarded command executor (user): single shared mechanism for money-moving writes: dedupe identity (client key | partner_event_id | none when naturally idempotent) -> one transaction -> guarded transition -> lock order -> effects (journal+lines, status_history, outbox) -> record outcome. Keys required only for operations that create something or move an amount; status-guarded transitions on existing rows are naturally idempotent.
- (question) Handoff to bmad-ux at finalize: client keeps the in-flight Idempotency-Key in sessionStorage so a reload mid-request reuses it; after reload the result shows in history before the user can confirm again. Confirm button disabled after first tap (UX nicety, not the guarantee).
- (decision) Idempotency at HTTP edge (user): custom @Idempotent() (SetMetadata + NestInterceptor) only marks the route as requiring Idempotency-Key, validates it (UUID, 400 if missing) and passes it down. Dedupe lives inside CommandExecutor.execute() in the business transaction, never in the interceptor (outside the tx, concurrent duplicates would both pass).
- (decision) Explicit row locks (user): LedgerService.post() locks all touched accounts with SELECT ... FOR UPDATE ORDER BY id before applying lines. Any read-aggregate-then-decide check (FR-4/FR-11 deposit/withdrawal limits, FR-24 transfer limit, FR-21 posting rate limit) first locks the user's available account row for that currency FOR UPDATE. Prevents: write skew (e.g. two concurrent withdrawals both passing a 5,000/30d limit).
- (decision) Isolation level (user): READ COMMITTED for all write paths; relies on Postgres re-evaluating UPDATE WHERE after waiting on a locked row. No SERIALIZABLE retry loops. Prevents: builders mixing isolation levels and ad-hoc retry logic.
- (decision) Reconciliation, statements and reports run as REPEATABLE READ READ ONLY transactions (consistent snapshot; read-only RR never raises serialization errors). Prevents: false SM-2 imbalance alarms from mid-scan commits; totals disagreeing with rows.
- (direction) SERIALIZABLE deferred. Revisit if the FR-24 linked-wallet self-match check needs a graph query that row locks on taker/maker accounts cannot cover.
- (decision) Quote vs exchange (user): separate entities. quote = disposable preview row (user, target offer|house, side, captured price, mid snapshot, expires_at = now + lock window), created per preview, no idempotency key, prunable. exchange = created once at confirm via guarded command, references quote_id; take validates lock owner, expiry, issued after last pause start, offer open + remaining, price not worse than house at lock time; settles at the quote's price. Mirrors Wise quote -> transfer. Prevents: abandoned previews polluting FR-3 history; mutating a financial record.
- (decision) Offer pricing storage (user): fixed offers store their price; pegged offers store only the margin, effective price = mid x (1 + margin) computed per tick, never persisted on the offer. Every exchange stores the actual price used plus mid snapshot (mid, mid_at, feed sequence) and the spread/margin applied, enabling SM-1 verification. No tick history table; latest mid only.
- (decision) Feed direction: backend subscribes to the FX feed (push); UI never reaches FX; UI receives rates from our backend over WebSocket. Rejected: per-request FX queries (latency, quotas, makes FR-15 impossible).
- (decision) Multi-instance rate distribution and event fan-out (user, option C): wallet-worker ingests the FX feed, upserts a single latest-rate row in Postgres and sends NOTIFY; outbox relay also NOTIFYs. Every wallet-api instance LISTENs on a dedicated connection, keeps latest rate in memory, pushes to its WebSocket clients, and re-reads latest state on reconnect (NOTIFY is not durable). Staleness (FR-15) judged from the DB row's timestamp so all instances agree. Rejected: every instance subscribing to the feed (N connections, instances disagree on pause); polling the rate row.
- (decision) Runnables (user): wallet-api = N stateless instances (REST + WebSocket) behind a load balancer; wallet-worker = separate entry point of the same codebase running exactly-one jobs (FX ingest, staleness watchdog, outbox relay, expiry/timeout jobs). Pilot: worker runs as a single instance. Worker failure is fail-safe: ticks stop, FR-15 pauses the board everywhere.
